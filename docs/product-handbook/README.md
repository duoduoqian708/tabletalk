## 给 AI 助手的操作指引（你是 AI 请从这里开始读）

你将在这个仓库里执行开发任务。本目录 9 个文件是产品的完整蓝图，**不要试图一次读完所有文档再开工**--它们是按问题类型索引的工具书，不是教材。按下面的协议工作：

### A. 标准任务循环（每个任务都走这一圈）

```
1. 领任务    任务来自 06 路线图的某一行（如 "Phase 0 · 星图 D1"），或用户直接点名（如 "做 02 的 C1"）
2. 读需求    打开 02-feature-specs.md 找到对应条目，读完 目标/用户故事/功能逻辑/涉及模块/验收标准
            ——这是本任务唯一需要完整精读的内容
3. 查规范    只查与本任务相关的节（见 B 表），例如写星图交互前必读 03 §5 的行为基线
4. 对齐      用两三句话向用户复述你对需求的理解（做什么、不做什么、怎么算完成），确认后再动手
5. 实现      遵守 C 节的硬性规则
6. 验收      把 02 条目和 06 任务行的验收标准逐条对照，逐条报告 通过/未通过 及证据（测试输出、命令结果）
7. 同步      实现中发现文档有缺口或错误 -> 先改 02/对应文档，再改代码，两者一起交付
```

### B. 按需查表（做什么查什么）

| 你正在做 | 必读 | 节 |
|----------|------|-----|
| 判断一个功能该不该做 | 01 | §6 六条设计原则、§7 反目标表 |
| 开发任何功能前 | 02 | 对应条目（A 可信 / B 安全 / C 方便 / D 星图 / E 团队 / F 开源） |
| 画界面、写组件、定交互行为 | 03 | 对应节；星图相关必读 §5 行为基线（标"勿回退"的行为禁止改动，除非先改文档） |
| 写任何 CSS / 选颜色 | 04 | §1-§4；颜色一律引用 tokens.css 变量，禁止硬编码色值；新颜色先进 04 再用 |
| 改后端结构、加依赖 | 05 | §2 架构原则、§6 依赖禁令；动到技术债相关代码先看 §5 |
| 动知识库 / 检索 / 向量 / 图谱 | 07 | §6 检索公式、§7 路由不变式（改公式先改文档）、§8 演进守则 |
| 排期、立项、结项 | 06 | 对应 Phase 任务表与退出条件 |
| 对外沟通、写文案 | 00 | 全文 |

### C. 硬性规则（违反任何一条都算做错）

1. **先文档后代码**：02 里没有的功能条目，先补条目（含验收标准）经用户确认，再实现。
2. **单一事实源**：路线图以 06 为准、北极星指标以 01 §8 为准（00 里的副本只是论述）；改这些内容只改事实源。
3. **颜色禁硬编码**：UI 一律引用 `frontend/src/renderer/src/styles/tokens.css` 的变量；语义色只用于语义（REVIEW 永远 amber，BLOCK 永远 red）。
4. **守门逻辑本地化**：闸门 / 脱敏 / 路由必须是本地纯函数、离线可跑、可审计；模型只负责"写"，永远不负责"放行"（01 §6 原则 2）。
5. **行数据不出网**：任何 AI 请求管道的改动不得绕过 05 §3 的单管道约束。
6. **文档代码同步**：改了行为却不改 03/04/05/07 对应描述 = 未完成任务。
7. **反目标红线**：BI 仪表盘 / 重型 RAG / 跨库联邦 / 通用 chatbot / 星图 2D 切换，一律不做（01 §7）；用户要求做时，先引用该节与其确认是否推翻决策记录。
8. **验收即结项**：验收标准是可测的（"审计 100% 含 reasons"），不是"体验良好"；测不过就是没做完。
9. **测试纪律**：后端 pytest 全绿是合并前提；星图交互改动必须跑 e2e 回归（像素断言法，禁止依赖人工看截图）；gate 攻击测试集任何一条由拦转变即 CI 失败。

### D. 起点与顺序

- 当前阶段：**Phase 0**（见 06）。建议顺序：技术债清场（05 §5 债 #7/#8）-> 星图 D1-D4 -> e2e 固化 -> License/M5。
- 上一 Phase 的退出条件未达成，不开启下一 Phase（06 各 Phase 退出条件）。

### E. 环境速查

```bash
python3 backend/tabletalk.py        # 一键启动（venv+依赖+前端构建+服务+浏览器）
cd backend && .venv/bin/python -m pytest -q          # 后端全量测试
cd frontend && npm run typecheck && npm run build     # 前端门控
cd frontend && npm run screenshot                    # Playwright 截图验证
```

代码现状的权威描述在仓库根 `CLAUDE.md`（每次会话自动加载）；本手册描述的是"该长成什么样"。两者冲突时：手册赢方向，CLAUDE.md 赢现状细节--即按手册改代码，顺手改 CLAUDE.md。

## 一页速览（人类读者从这里开始）

- **定位**：让人人敢查数据库，让企业敢让 AI 进数据库。
- **三支柱**：可信（主线，服务企业/DBA）· 方便（副线，服务不写 SQL 的人）· 安全（基础，让前两者在外网大模型时代成立）。
- **安全主张**：行数据永不出内网；出网的是脱敏后的结构与聚合；每一笔列在清单里、记在审计里。
- **统一叙事**：闸门 + 脱敏 + 出网清单 + 审计 = **本地可信层（TrustCore）**--不依赖任何模型的本地防线。
- **节奏**：第一期开源个人版（口碑与社区）-> 第二期安全落地（过合规评审）-> 第三期团队网关（商业化验证）。
- **反目标**：不做 BI / 不堆重型 RAG / 不做跨库联邦 / 不做通用 chatbot / 星图不做 2D-3D 切换。

## 使用约定（对所有读者的三条）

1. 功能开发前先在 02 找到对应条目；没有的功能先补文档再动手。
2. 交互行为与 03 冲突时，改文档 + 改代码同步进行，不允许"代码先行、文档欠账"。
3. 本手册允许被推翻--但推翻要在 01 §9 决策日志留记录（只追加不删除）。
