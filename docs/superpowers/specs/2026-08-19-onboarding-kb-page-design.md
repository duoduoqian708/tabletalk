# 数据源接入流程 + 知识库页设计（DATUM V2 补充）

> 状态：设计定稿（2026-08-19）。只写设计，未动代码。
> 关联：`2026-08-19-datum-v2-vision-design.md`（V2 总愿景）、`2026-08-19-datum-v2.md`（P1–P6 实施）。

## 1. 背景与目标

现状痛点：连接保存即算"接入"，但**知识库懒构建**——用户第一次提问 AI 时才临时抱佛脚，卡顿且不可预期；知识库与图谱是 V2 的核心差异化，却藏在后台。

目标：把"接入"变成一个有仪式感的完整流程——**验证 → 落盘 → 强制构建 → 一键确认**，构建全程自动、带进度、可审查；知识库与图库合并为一页，构建完即可审可改。

## 2. 接入流程总览（状态机）

前置条件：**LLM 已配置**（未配置则引导去设置，不允许进入接入流程）。嵌入模型未配置时不阻塞，构建降级为"词面+图谱检索"，界面上持续显示"语义嵌入未启用"徽标（沿用现有行为）。

每数据源有 `kb_status`，取值：`none`（未构建）→ `building`（构建中）→ `pending_review`（待确认）→ `ready`（已就绪）。

```
填表单 → 点测试
   ├─ 失败/未测试 → 草稿态（仅浏览器缓存），保存按钮不可点
   └─ 通过 → 写入后端 connections.json（正式连接）→ 保存按钮可点
保存成功 → 弹窗"是否立即构建知识库（含图谱）？"
   ├─ 同意 → 后台构建任务 + 进度条（阶段上报）→ 构建完 → pending_review
   │         → 跳到知识库页 → 用户查看/编辑 → 点「确认启用」→ ready
   ├─ 拒绝 → kb_status=none（记在该数据源上），不阻塞页面操作
   │         → 切回该数据源时再次弹窗（一直弹到构建完成为止）
   └─ 未构建状态 = 该数据源不可用（见 §3.4）
```

### 2.1 草稿态（浏览器缓存，不进后端）

- 表单内容存 `localStorage`（键 `cleared-conn-drafts-v1`，按数据源特征分组）。
- 用户填一半切走（比如去找正确密码）、表单刷新回来自动回填。
- **测试通过才从缓存删除并 POST 到后端**——后端配置文件只收"验证过的连接"。
- 后端 `connections.json` 增加非敏感元数据字段：`kb_status`、`kb_updated_at`（操作状态，不是凭据）。

### 2.2 测试前置（必须先测才能保存）

- 新增端点 `POST /api/v1/connections/test-draft`（body = 连接配置，**不落盘**），返回 `{ok, latency_ms, error}`。
- 前端：保存按钮在"最近一次测试通过 **且** 表单自测试后未改动"之前始终禁用；表单任何字段被改 → 保存按钮立即回到禁用并提示"请重新测试"。
- SQLite 额外处理：没有"库"概念，测试=打开文件 + 能列出表（文件可读即视为通过）；文件路径为空直接判失败并提示"请选择 SQLite 文件"。其余方言按"连服务器 → 选库"的真实链路测到具体库。

## 3. 构建（最复杂的环节，全自动 + 进度条）

### 3.1 任务化

- `POST /knowledge/{id}/build` 改为**创建后台任务**，立即返回 `{job_id}`；进度通过 `GET /knowledge/{id}/build/progress` 轮询（500ms）。
- 任务阶段（每阶段报 percent 与文案）：①发现结构 → ②抽样取值 → ③生成注释文档 → ④构图（FK 边 + 值重叠边）→ ⑤向量化（文档级 + 表级）→ ⑥落盘。
- 支持取消（`POST /knowledge/{id}/build/cancel`）：取消后 `kb_status` 回 `none`，可重新构建。
- 任务与前端解耦：用户切换数据源/关掉构建弹窗，构建继续跑；回来看到 `building` 进度。

### 3.2 构建产物（沿用现有 KnowledgeBase）

文档（表/列注释草案）、领域标签草案、图谱（FK 边 + 值重叠边）、文档级向量 + 表级向量、落盘 artifact。

### 3.3 确认闸（AI 不能给自己盖章）

- 构建完成后 `kb_status = pending_review`，**自动跳转知识库页**，顶部出现"构建完成 · 请查看内容并确认"。
- 确认前：标签不参与"问题→选表"路由（安全约定保留）；图谱与文档可正常浏览。
- 用户可**编辑/修正**文档内容、标签（改名/驳回）、表级标签、删除推断边，然后点一次「确认启用」→ `ready`。
- **确认后仍可继续编辑**——确认只是解锁路由的闸门，编辑是常态；确认后标签与边立即参与路由。

### 3.4 未构建 = 该数据源不可用（卡死，但不阻塞页面）

- 后端：`kb_status != ready` 时，该连接的所有查询入口返回明确错误码 `kb_not_built`（手动 `POST /query`、AI chat、schema 之外的取数接口）。
- 前端：拦截 `kb_not_built` → 弹构建窗（同意 / 稍后）。「稍后」只关弹窗，**不阻塞页面操作**——用户仍可切换、管理其它数据源；切回该数据源时再次弹窗。
- 弹窗频率控制：同一次会话内对同一数据源只弹一次，关闭后不再骚扰（直到主动切换）。

## 4. 知识库页（知识库 + 图库合并为一页）

### 4.1 布局

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：连接名 ▼  状态徽标 [构建中 68% | 待确认 | 已就绪]   重建 │
├───────────────────────────────┬──────────────────────────────┤
│  左区 · 知识库内容（42%）      │  右区 · 图结构预览与编辑（58%） │
│  ┌─────────────────────────┐  │  ┌─────────────────────────┐  │
│  │ [搜索框] 检索全库        │  │  │ [缩放− + 适应 关系:◉全部  │  │
│  │ [文档] [标签] 子标签页   │  │  │  ◉FK ◯值重叠]           │  │
│  │ 文档卡片列表             │  │  │ 画布: 表节点+关系边      │  │
│  │ · 标题/摘要/来源徽标     │  │  │ (选中表→浮层详情/编辑)   │  │
│  │ · 待确认/已确认 状态     │  │  └─────────────────────────┘  │
│  │ · 点击展开可编辑         │  │                              │
│  └─────────────────────────┘  │                              │
│  底部: 文档 N · 标签 M        │                              │
├───────────────────────────────┴──────────────────────────────┤
│ 底部状态条: 嵌入模型徽标 · 最后构建时间 · 待确认 N 项          │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 左区 · 知识库内容

- 搜索框：复用现有 retrieve（top-N 召回）。
- 子标签页 **文档**：卡片列表，每表/列一条注释文档；卡片含来源徽标（自动生成/草稿/用户）、状态点（待确认/已确认）、正文预览；点击展开**就地编辑**。
- 子标签页 **标签**：领域标签库 + 每表表级标签；卡片显示名称、覆盖表数、状态；可确认/驳回/改名/新增。
- 底部统计：文档数 · 标签数 · 关系边数。

### 4.3 右区 · 图结构预览与编辑

- 画布复用 GraphCanvas 交互（节点=表、选中高亮、平移缩放、适应视图、k-hop 语义沿用）。
- **关系过滤**：FK 实线 / 值重叠虚线，可单独开关（默认全开）。
- **值重叠边**：边上小字显示重叠列与强度（可审可信的关键）；**允许删除**（推断边可删误报），删除记入墓碑（见 §5，重建不复活）。
- **FK 边只读**（数据库结构事实，删除会误导路由）。
- **节点浮层**：表名、字段列表、注释（可改）、该表标签（可加可确认）。
- 编辑产生"未保存修改"标记；本轮范围：预览 + 节点编辑；**加边/删边 UI 留到下一轮**（接口先留）。
- 确认闸与编辑：`pending_review` 时可编辑；「确认启用」后仍可编辑。

### 4.4 风格（对齐 Void 深空）

- 深空黑渐变底（--void-0 系）；左右暗色面板（--void-2 卡片 + 1px --line 描边 + 微光投影）。
- 强调色仅电光紫 #7c8cff：状态徽标、确认按钮、选中节点光圈。
- 等宽字体（IBM Plex Mono）：表名、边标签、状态文本；正文系统无衬线。
- 状态色克制：待确认=琥珀点，已确认=紫点，构建中=紫呼吸动画；过渡 120–180ms。

## 5. 定期增量更新（后续阶段，本设计留位）

- **触发**：周期任务（运行时配置，如每 30 分钟）+ 手动"检查更新"；用 schema 指纹（表/列/FK/注释哈希）对比上次构建。
- **增量范围**：仅处理变化部分——新增表 → 新文档+新节点+向量；注释/标签变化 → 更新对应文档与表级向量；FK 变化 → 增删边；删除的表 → 文档标记"已删除"（不物理删，可回溯）。
- **不重建全部**：只对变化表重算表级向量与文档向量。
- **用户编辑保护**：增量只更新"自动生成"来源的文档，不覆盖用户手改内容（来源徽标区分）；用户删除的值重叠边写入**墓碑列表**，重建/增量不复活。
- **增量与确认闸**：增量产生的新文档默认 `pending_review` 状态（沿用"AI 不能给自己盖章"），可在知识库页一次确认全部增量。

## 6. 后端 API 草案（实施时再细化）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/connections/test-draft` | 测试不落盘，body=配置；SQLite 走文件可读判定 |
| POST | `/api/v1/knowledge/{id}/build` | 建后台任务，返回 job_id；kb_status→building |
| GET | `/api/v1/knowledge/{id}/build/progress` | 轮询：{stage, percent, done} |
| POST | `/api/v1/knowledge/{id}/build/cancel` | 取消；kb_status→none |
| POST | `/api/v1/knowledge/{id}/confirm` | 确认启用；kb_status→ready，标签/边参与路由 |
| GET | `/api/v1/knowledge/{id}/status` | kb_status + 最后构建时间 + 待确认数 |

- 未构建拦截：查询入口返回 `{error: {code: "kb_not_built"}}`（HTTP 409），前端据此弹构建窗。
- `kb_status` 持久化在连接配置元数据；构建产物仍在知识库存储（SQLite storage / JSON 兜底）。

## 7. 风险点与待定点

1. **构建中用户离开**：任务后台继续，状态持久化；重建/重进不会重复构建（building 幂等）。
2. **大库构建时长**：进度条 + 可离开 + 可取消；API 嵌入器逐条调用是主要耗时，批量向量化已就位。
3. **确认闸与全自动的平衡**：已定"整体确认闸"，确认前不参与路由——这是产品安全卖点，不在体验上拆掉。
4. **增量 vs 手动编辑冲突**：来源徽标区分 + 墓碑机制，增量不覆盖用户内容（§5）。
5. **待确认/已确认的路由语义**：确认前的标签不参与路由但参与展示；文档级向量不含未确认标签，避免隐式泄漏（实施时核对 `_embed_table_docs` 的 confirmed 过滤是否已覆盖此语义）。
6. **SQLite 无库**：测试路径与 PG/MySQL 分离，判定标准放宽为"文件可读 + 能列表"。
7. **浏览器草稿与后端一致性**：草稿仅 UI 层回填，不参与任何后端逻辑；多标签页同开时以最后写者为准（localStorage 原语，可接受）。

## 8. 向量库通用化（chunk + 元数据区，扩展预留）

### 8.1 现状核实（2026-08-19 代码）

- vec0 表只有 `{id, vec float[256]}` 两列，无元数据；维度写死 256（`_pad256`），真语义嵌入（如 doubao 2048 维）下实际检索走内存 BatchIndex，vec0 仅作持久化/查询表达力演示。
- `BatchIndex` 模型是裸 `{id: vector}`，无 metadata；上层靠 `_vec` / `_table_vec` 两个硬编码字典区分用途，每加一种用途就要硬编码一套。
- sqlite-vec vec0 允许额外列作 metadata（可存可读），但 KNN 查询内 WHERE 过滤语义受限，官方推荐应用层过滤——而我们的 numpy 全量算分天然支持"先过滤再算"，零额外成本。

### 8.2 统一 chunk 模型（核心设计）

```
VectorChunk {
  id, conn_id,
  collection   # 用途分类：doc | table | enum | intent | alias | ...（可扩展）
  text         # 内容原文（可展示、可做关键词融合）
  metadata     # 自由元数据区（任意键值，可过滤）
  vector, fingerprint, updated_at
}
```

一切用法 = 向同一个池子放入带 collection 标签的 chunk。规划 collection：

| collection | 内容 | metadata 示例 | 用途 |
|---|---|---|---|
| doc | 表/字段注释文档（auto/drafts/user 归一） | `{source, status}` | 现有能力，不破坏 |
| table | 表级向量 | `{table}` | 问题→表定位 |
| enum | 字段枚举取值样本 | `{table, column, value}` | AI 生成 SQL 时检索合法取值 |
| intent | 意图样本→标签 | `{intent}` | 意图识别（向量兜底/加速标签路由） |
| alias | 同义词→规范名 | `{canonical}` | 语义统一（退货↔returns 归一） |

### 8.3 检索接口

`search(q, collection=None, filter=None, k=10)`：先按 collection + metadata 键值筛候选 id 集，再算相似度；numpy 下即"先筛行再矩阵乘"，几万条毫秒级。关键词/图谱融合路径不变。

### 8.4 存储与迁移

- vec0 表加 `collection` + `metadata TEXT(JSON)` 列；维度按嵌入模型实际维度建表，不再写死 256。
- KbSnapshot 增加 `chunks` 字段（新写入归一为 chunk）；旧字段 `vec/table_vec` 保留兼容，读取时迁移为 `collection=doc/table`。
- 确认闸语义保持：未确认标签不进表级向量（`_embed_table_docs` 的 confirmed 过滤为最低标准）。

### 8.5 企业版对齐

过滤能力在 KbStorage 协议层表达（`search(filters, k)` 或 `vec_filtered_topn_sql`）：pgvector 用 `metadata @> ?` + `ORDER BY vec <=> ?` 原生过滤；Qdrant 用 payload 过滤。上层不变，换实现即可（呼应"更换组件成本低"）。

### 8.6 风险

1. 迁移兼容：旧 artifact 读取路径需保持到下一版本，避免破坏已建库用户。
2. vec0 维度随模型变化：重建时按指纹重建表（与 reembed 联动）。
3. 多 collection 混合检索：关键词融合按 collection 加权，需在实施时定默认权重。

### 8.7 实现方案（已确认 2026-08-19）：VectorStore 分层

**原则**：业务代码只认识 VectorStore 的业务语义接口，不认识任何厂商 API；换底层 = 换一个实现文件，业务零改动。这是个人项目"自研"的稳妥姿势——不是不换，是换的时候只动一处。

**三层结构**：

```
业务层（KnowledgeBase / AI 路由 / 检索融合）
   ↓ 只依赖
VectorStore（统一接口，业务语义）
   ├─ NumpyBackend      ← 默认主检索：内存 numpy 矩阵，归一化预处理在内部统一完成，
   │                      几万条全量余弦毫秒级，collection+metadata 过滤零成本
   ├─ SqliteVecBackend  ← 持久化实现（现在）：vec0 虚拟表，负责落盘/恢复/审计
   └─ LanceBackend      ← 未来接入（触发信号：10万+条 / 多模态 / 多进程共享检索，
                          优先 LanceDB；0.x API 变动频繁，接入时锁版本）
```

**Pydantic 数据契约**（跨后端的唯一中间语言，替代裸 dict）：

```
VectorChunk { id, conn_id, collection, text, metadata, vector, fingerprint, updated_at }
SearchQuery { qvec, collection?, filter?（metadata 键值）, k }
SearchHit   { chunk: VectorChunk, score: float }   # 距离统一换算为相似度
```

- `VectorChunk` 取代 `_vec` / `_table_vec` 两套裸字典（归一为 collection=doc/table，兼容 §8.2 分类表）。
- numpy 归一化在 VectorStore 构造时统一完成（现状 BatchIndex 已如此，升级为契约）。
- 接口只暴露业务形状（`search(q, collection, filter, k) → SearchHit[]`），不泄漏 vec0 的 `distance`/MATCH 或 LanceDB 的 `.where()` 等厂商形状；维度由 embedder 决定、VectorStore 构造时固定，调用方无感。
- 诚实边界：vec0 全表扫描未必快于内存矩阵乘、维度写死 256、无原生过滤——故默认主检索是 NumpyBackend，SqliteVec 只做持久化；LanceDB 接入时数据迁移 + 契约测试各跑一遍，切换动作本身按半天到一天评估（对外不承诺"1 小时"）。
- 数据流：构建期 BatchIndex 仍可作构建工具；检索主路径统一走 VectorStore，`vec_topn_sql` 升级为 SqliteVecBackend 内部实现。
