# CLEARED — 分析报告模式设计文档

日期：2026-08-16 · 状态：设计已定（待实现）· 前序决策见 `2026-08-13-ai-dbclient-design.md`

## 0. TL;DR

**新能力**：用户用自然语言要一份报告（"出 Q3 销售分析报告"），系统多轮澄清口径后排一份章节化的报告，每章 = 数据查询（过安全闸门+审计）+ SVG 图表 + 引用真实查询结果的叙述，渲染成报告卡。

**架构判据**：**不开新智能体**。报告是现有单智能体（function-calling 循环）的一种新模式（mode），不是新智能体。

**三条已锁定决策**：
1. **动态结构**：章节由 LLM 规划，但每章固定三件套（数据/图表/叙述）；**不固定模板**，不纯放养。
2. **快照数据**：报告生成时刻的数据固化进报告，重开看的是生成时的数（与审计"某一刻执行"叙事一致）。
3. **多轮澄清**：报告流是可被澄清打断的状态机，不是一次性 SSE 跑完。
4. **报告独立闭环**：不复用会话历史里的查询结果。报告自己的子查询才是数据来源。

## 1. 为什么做，为什么是 mode 不是 agent

### 价值

现有闭环是"查数"：问一句 → 一条 SQL → 一张表。报告是"分析"：给目标 → 多步查询 → 图表+结论。是能力台阶，不是平行 feature。三个既有资产恰好为它准备：

| 既有资产 | 报告里怎么用 |
|---------|------------|
| 知识库领域标签 | 报告规划（"Q3 销售该看哪些数"）用标签路由找相关表 |
| 安全闸门 | 一份报告 = 十几次闸门调用。叙事：**"报告里每个数字都能回溯到一条被安全评估、被审计的 SQL"** |
| 审计 | 报告 = 一条完整查询痕迹链，企业审计硬需求 |

加一个天然优势：**报告模式物理上只读**——工具集根本不放 `run_dml`/`draft_ddl`，和"DDL 不进 AI 工具集"是同构逻辑，写操作的闸门连用都用不上。

### 为什么不开多智能体

现状已是单智能体：function-calling 循环（`app/ai/loop.py`：`provider.chat` + `execute_tool` + SSE）就是标准智能体形态。报告需求规划/取数/分析/写叙述/选图表，同一份循环+不同工具集+不同输出格式可做完。多智能体的真正判据报告一条不沾：

| 判据 | 报告需求 |
|------|---------|
| 异构模型分工（便宜模型分类、贵模型分析） | 各环节同一模型即可 |
| 并行自主运行、互相协调 | 顺序流水线 |
| 独立失败域 | 单循环失败即中断 |
| 独立部署的自治组件 | 只是聊天的一个模式 |

→ **mode 路由**：意图分类多一个 `report` 分支，同一套 loop 挂只读工具集 + 报告 system prompt。

### 什么是该上多智能体的需求（留档对照）

后台自主巡检——智能体夜里自己跑分析、发现异常主动汇报——有自己生命周期、独立运行，那才是多智能体出场时机。报告不是。

## 2. 三条安全/隐私不变式（与既有哲学同构，不是新规则）

| 既有约束 | 报告对应约束 |
|---------|------------|
| 每条 SQL 过闸门 | 每章每个数字来自真实查询 |
| DDL 不进 AI 工具集 | 报告工具集不放 `run_dml`/`draft_ddl` |
| 执行必进审计 | 每章子查询照常审计 |
| 行数据默认不回模型 | 图表数据只传聚合结果（GROUP BY 后统计值），原始行依旧不回传 |

红线不变形，只点出一点：**报告绕不开"数据要回模型"**（看不到聚合数没法写结论）——所以报告模式把"回模型"的范围明确画在**聚合结果**，报告卡上明确标注"模型可见：N 个聚合结果集"。

## 3. 报告流总形态

```
用户:"给出 Q3 销售分析报告"
  └─ 意图路由: report 分流
      ├─ 澄清子循环(多轮,≤3问): 口径/时间范围/维度/受众
      │     每轮 yield 一个澄清问题 → 暂停 → 等用户答 → resume
      ├─ 分析计划: schema 化章节列表
      │     [{id, title, intent, chart_hint, depends_on_chapter}]
      ├─ 逐章执行: 每章复用现有查询闭环
      │     标签路由→run_query(过闸门)→拿 result_id → 注册进报告上下文
      │     (渐进式 SSE: 每章完成推一个 section 事件)
      ├─ 汇总成文: 各章 result_id 对应的聚合数据集喂回 LLM
      │     叙述里数字强制引用 result_id
      └─ 报告卡渲染
```

**两个关键点**：
- "分析计划"那步**必须结构化输出**（schema 化章节列表，不是一段话），否则前端没法控、数字回溯不了。这是这套设计的杠杆。
- "澄清"那步**必须能把 loop 在中途挂起**，等下一轮用户输入再 resume——这是 mode 化最不平凡的一处，见 §6。

## 4. 触发方式

- **自然语言主路径**：意图分类把"出报告/分析/趋势/总结"分到 `report` 分支进报告流。
- **按钮兜底路径**：输入框旁加「报告」按钮，点了直接进报告流、**绕过意图分类**，进第一个澄清问题。消掉"是查询还是报告"的模糊判别。

两路殊途同归，进同一个报告流。

## 5. 阳/阴 turn 并存的会话模型

一个会话是一串 turn。每个 turn 要么 query 模式（现状）要么 report 模式：

```
会话
 ├─ turn1 query  : "查退货率"             → 1 SQL → 1 表
 ├─ turn2 query  : "按月看销量"           → 1 SQL → 1 表
 └─ turn3 report : "出 Q3 销售分析报告"   → 1 报告流(独立闭环)
      ├ chap1 销售总览 : 2 子查询(过闸门+审计) → 柱图 + 叙述
      ├ chap2 渠道占比 : 1 子查询            → 饼图 + 叙述
      └ chap3 异常订单 : 2 子查询            → 表 + 叙述
```

**报告不从历史 turn 挑数据**：报告数据来自它自己跑的子查询。历史 turn 结果仍留在会话里随时回看，报告不碰它们。

> 可选（第一版不做）：报告规划时让 LLM **看到**会话历史问过什么（只传提问文本，不传结果行）作规划参考。纯独立最干净，第一版先不做。

## 6. 多轮交互的技术形态

报告流不是"一次性 SSE 跑完"，而是可被澄清打断的状态机：

```
启动 → 澄清问1 → 挂起等用户答 → 用户答 → 澄清问2? → ...
     → 计划完成 → 逐章执行(SSE 推 plan/section/narration) → 报告卡
```

**为什么这一处不平凡**：现在 `chat_stream` 是一个一次性 async generator，一口气 yield 到底。报告模式需要在澄清点 **yield 一个澄清事件后挂起**，等下一轮 `POST /ai/chat` 带着用户的澄清答案进来，再从中断点 resume。

这是新的、报告独有的请求形态，但不是新架构——与 chat 本身的多轮是同一套机制（前端带完整历史，后端无状态）。落地形态：

- 报告流的状态由前端持有：已问的/已答的/已执行的章节。
- 后端 `chat_stream` 增加一份"报告模式"的 generator，在澄清点 yield `{"type":"clarify", ...}` 后自然结束当前 SSE（done）。
- 前端收到 clarify 事件后渲染澄清输入，用户答完用新一次 `POST /ai/chat` 把完整的"报告历史"（含已答的澄清）重传，后端 replay 到断点继续。

→ **关键不变式**：后端依旧无状态，前端始终持有报告中间态。与现有 chat 的无状态哲学一致，不引入服务端会话状态。

## 7. 事件契约（SSE 事件增量）

现有事件：`turn_start` · `text` · `think` · `sql_card` · `done` · `error`。

报告模式新增事件（共用同一个 SSE 流，前端按 `type` 分流）：

| 事件 | 何时发 | 载荷 |
|------|-------|------|
| `report_start` | 报告流启动 | `{connection, snapshot_ts}` 快照时间戳 |
| `clarify` | 需要澄清时 | `{question, field, options?}` 一问一答 |
| `plan` | 分析计划完成 | `{sections: [{id, title, intent, chart_hint, depends_on_chapter}]}` |
| `section` | 单章执行完 | `{id, title, result_id, chart:{kind, data}, rows_preview, elapsed_ms}` |
| `narration` | 叙述块产出 | `{section_id, text, refs:[{result_id, value}]}` 数字挂来源 |
| `report_done` | 报告完成 | `{summary, section_count}` |

**数字回溯**（轻量版，第一版）：`narration` 的 `refs` 里每个数字挂 `result_id`，前端能 link 跳到该章查询/审计。不做"叙述 vs 数据自动核对"（留接口，第一版不做）。

## 8. 报告卡形态（前端）

结果区现在只有"表格"一种形态，报告模式新增"报告"形态。报告卡 = 一串章节卡，每章：

```
┌─ 报告卡 · Q3 销售分析 · 快照 2026-08-16 14:30 ───────┐
│  分析目标 / 快照时间 / 数据源 / 章节数            │
├──────────────────────────────────────────────────┤
│ ▸ chap1 销售总览                                 │
│   叙述:"Q3 总销售额 ¥1.2M¹，环比 +12%²…"          │
│   柱图(SVG 北欧线条, 月度)                        │
│   数据块(折叠的 DataTable, 点开看明细)          │
│   ├ 这是 result_id=r1 的子查询结果                │
├──────────────────────────────────────────────────┤
│ ▸ chap2 渠道占比 …                                │
└──────────────────────────────────────────────────┘
  ¹跳到审计 r1  ²跳到审计 r2  (数字回溯)
```

视觉复用北欧极简（白面板 14px 圆角、细边框、蓝强调、Hanken Grotesk）；SVG 图表块复用知识图谱那套北欧线条风。隐私标注常驻："模型可见：N 个聚合结果集"。

## 9. 后端改动（mode 化，不动核心）

**不改智能体架构，给现有 loop 加一个 mode 配置**：

- `app/ai/schemas.py`：`ChatRequest` 加 `mode: Literal["query","report"] = "query"`。
- `app/ai/intent.py`：意图分类加 `report` 分支（关键词"报告/分析/趋势/总结/概览"+ LLM 判定，mock 关键词回退）。
- `app/ai/loop.py`：
  - `chat_stream` 按 `mode` 分流；`mode=="report"` 走 `report_stream`（新 generator，复用 `provider.chat` + `execute_tool`，挂**只读工具集**）。
  - `MAX_TURNS` 报告模式上调（报告比单查询多几轮）。
- `app/ai/tools.py`：新增 `TOOL_SCHEMAS_READONLY = [get_schema, describe_table, run_query]`，砍掉 `run_dml`/`draft_ddl`。报告模式只用这个子集。
- `app/ai/context.py`：新增 `report_system_prompt()`——报告角色 prompt（快照口径、章节三件套、数字挂 result_id、聚合优先）。
- 新增 `app/ai/report.py`：报告流 generator（澄清→计划→逐章→汇总），产出 §7 事件。
- 快照：`report_start` 携带 `snapshot_ts`；该报告所有子查询的审计记录挂同一个 `report_id`（审计加可选字段，见 §11），便于从一个报告回溯全部子查询。

**工具集决策**：报告模式只读 = 既不挂 `run_dml` 也不挂 `draft_ddl`。物理写不了，和"DDL 不进 AI 工具集"同构。

## 10. 前端改动

- `AiRail.tsx`：输入框旁加「报告」按钮（明确触发模式），点了前端直接 `mode:"report"` 发出去绕过意图分类。
- 新组件 `ReportCard.tsx`：报告卡（章节卡序列 + SVG 图表块 + 数字回溯 link）。
- 结果区 store 新增"报告"形态（区别于现在只有 `ResultSet | null`），可并存"当前报告"与"当前表格"。
- 报告流状态机：持有 `plan/answered_clarify/executed_sections`，收 `clarify` 事件渲染澄清输入，答完用新一轮回传。
- 字体/动画/配色复用既有北欧系统。

## 11. 审计与存储

- **审计**：每章子查询照常进审计；新增可选字段 `report_id`（一个报告的所有子审计挂同一 ID）。`GET /audit` 支持 `?report_id=` 过滤——一份报告的完整查询链一眼可见。
- **快照**：`snapshot_ts` 固化进报告卡。重开报告看的是生成时的数，不重跑查询。报告本身可序列化进会话消息（`kind:"report"`，含 plan + sections + narration），随会话历史回看。
- **会话语义继承**：报告 turn 仍只在"提问"时 upsert 会话+刷更新时间（含澄清答也算该 turn 的提问）、查看历史不刷时间、运行不碰会话——现有语义不动，只是多一种消息 kind。

## 12. 第一版收敛（避免摊太大）

- **图表只做 3 种**：柱/折线/饼，SVG 北欧线条风（复用知识图谱那套），覆盖分析报告 80%。
- **数字回溯做轻量版**：叙述数字挂 `result_id`，前端 link 跳审计；不做"叙述 vs 数据自动核对"（留接口）。
- **澄清只问 1 轮**（≤3问），不做无限追问。
- **不做 PDF 导出**，先在应用内呈现。
- **图表数据只传聚合结果**（GROUP BY 后统计值），原始行数据依旧不回模型——红线不动。
- 报告独立闭环，不复用历史 turn 查询结果（第一版纯独立最干净）。

## 13. 与原设计文档的关系

本文件是 `2026-08-13-ai-dbclient-design.md` §10「报表 HTML」方向的**演进与细化**。原 §10 偏"AI 写 HTML 模板、本地注入数据、自包含可分享文件"；本设计改为**应用内报告卡、动态章节、多轮澄清、数字回溯**——形态更适合 AI 优先叙事，也回到了我们一直强调的"安全闸门-审计-知识库"三资产的协同。

原 §10 的"可分享单文件 HTML"价值仍在（企业内部分享），可作为本报告的**导出格式**后续补：报告卡序列化 → 模板 → 自包含 HTML。第一版不做。
