# HITL 架构承载性评估

日期：2026-08-18 · 性质：架构承诺，回答"自研 ReAct 循环能否长期承载 HITL"的疑虑

## 背景

用户担忧：现在 HITL（人工确认）能实现，但"以后要做的东西"（真实向量库、AI 报表、团队网关）是否会逼架构大改，因此考虑引入 LangGraph 等 agent 框架。本文回答：**自研循环不仅现在承载 HITL，且比框架更稳**，并给出逐场景的演进路径。

## 结论一句话

HITL 在 TABLETALK 里是**环境级安全硬墙**（执行器强制），不是流程级"图节点暂停"——这决定了自研比 LangGraph 更贴合；引入框架不会消解未来改动风险，反而牺牲对安全闸门的绝对控制。

## 一、HITL 的两层实现（都已落地）

| 场景 | 技术形态 | 状态 |
|---|---|---|
| 写操作确认（INSERT/UPDATE/DELETE） | AI 生成 → `review` 卡 + 预估行数 → 用户 `confirm:true` 二次请求 → 执行。后端无状态，审批在两次 HTTP 之间，前端持中间态 | ✅ 已实现 + 真实 SQLite 验证 + 回归测试（`tests/ai/test_hitl_invariant.py`） |
| 报告澄清挂起/恢复 | `report_stream` → clarify 事件 → 前端渲染输入 → 用户答 → 前端重传已答历史 → 后端 replay 到断点继续 | ✅ 已实现 + 测试（report 澄清用例） |

## 二、为什么 HITL 是"环境级硬墙"而不是"流程级暂停"

- **执行器强制**：安全闸门是 `execute_tool` 的第一道拦截（`verdict` 非 allow 不执行），`run_dml` 工具物理上没有"自动执行"通道，永不返回 executed。这是**写死在执行器上的规则**，与"图怎么编排"无关。
- **产品承诺**：写操作确认是「执行权在人」的物理保证（PRD §7.9），不是可选的编排模式。**换框架反而要把这道硬墙嫁接到框架的工具钩子上，多一层适配、多一分绕过风险。**
- **回归锁定**：`test_hitl_invariant.py` 三条测试把"永不无确认执行"锁死，未来任何循环/工具/框架改动都必须先过它。

## 三、逐场景承载性 + 演进路径

| 场景 | 自研能否承载 | 演进路径（改的是"加层"，不是"推倒"） |
|---|---|---|
| 写操作 HITL | ✅ 环境级硬墙，永久成立 | 无（已锁死） |
| 报告澄清挂起/恢复 | ✅ 已实现 | 前端持状态 → 后端持久化为"加 session 存储 + 前端交 history"，逻辑不变 |
| 团队网关多用户会话 | ⚠️ 需加后端 session 存储 | 一次性"无状态→有状态"演进；与是否用框架无关 |
| 真实向量库/大模型 | ✅ 已抽象（Embedder/网关） | 见 §四 |
| 多智能体并行/独立失败域 | ⚠️ 现状用不上 | 报表/对话为单智能体；真到那天再评估 LangGraph |

## 四、为什么上 LangGraph 不会更好（反而更险）

1. **状态绑定**：LangGraph 的 `interrupt`/checkpoint 把状态和历史绑死在框架内部；换引擎/迁移状态反而是重活。TABLETALK 的"前端持状态+history 重传"是无状态架构，分布式友好，升级后端持久化是**加层**。
2. **安全旁路风险**：框架的 HITL 是"流程中断点"，我们的是"执行器硬墙"。框架化后要保证每一条工具路径都过闸门，适配成本高、易漏。
3. **YAGNI**：当前/近期（PG、真实向量、报表）都是单智能体 + 少量工具，LangGraph 的能力用不上，引入即给未发生的问题背债。

## 五、建议（把承载性变成"架构承诺"，而非靠感觉）

1. **[已做]** `test_hitl_invariant.py` —— 锁定"写操作永不无确认执行"。
2. **[可做]** 文档固化"两层 HITL"与"环境级硬墙"为架构原则（本文即起点）。
3. **[触发条件才做]** 团队网关出现时，才评估后端 session 持久化 / （若真需多智能体）LangGraph。

## 六、与决策总账的关系

本评估落实 PRD §7.9/§7.10 的「执行权在人」+「闸门任何级别不可关闭」；自研 ReAct 循环是这些保证的载体，不因接入向量库/报表/网关而改变。
