# CLEARED — 产品需求文档（产品设计）

- 日期：2026-08-18 · 状态：已定稿（多轮与负责人对齐，实现前可微调）
- 视角：产品设计（跳出既有实现，从用户价值出发）；现状只作锚点，不设牢笼
- 一句话：**"ask your database — nothing runs until it's cleared."**

---

## 0. 一句话与定位主张

**CLEARED 用一句话交付数据库洞察：开发者/分析师用自然语言向数据库提问，系统保证回答永远写不坏、走样有记录、数据不出网。**

定位主张不是"更聪明的 AI 写 SQL"，而是**把数据库变成一个你可以直接问、而且问不坏的对象**。能力会同质化（大厂都在做 text-to-SQL），信任不会——**我们的护城河是可验证的信任基础设施**：一个闸门管所有写入、执行权默认在人（信任级别可调）、每个数字都可回溯出处、数据边界由用户画。这才是 DBeaver 给不了、云厂商绑定不了的东西。

## 1. 机会与问题

数据库客户端的真实痛点从来不是"连不上库"，而是：

- **查数成本高**：为一个验证性想法写样板 SELECT、来回改 JOIN/WHERE，十分钟起步
- **上下文切换累**：想数在编辑器，懂语义在文档，验证结果在 psql
- **业务被"取数"卡脖子**：团队里不会 SQL 的人永远在排队等开发给数
- **AI 有信任赤字**：人们不担心 AI 写不出 SQL，担心它写出"危险 SQL"（没 WHERE 的 UPDATE、DROP 整个表）

现有供给各占一角：桌面客户端（DBeaver/Navicat）工具强但 AI 弱、无信任叙事；云厂商 text-to-SQL 聪明但绑定单云、隐私存疑；零散 AI 助手不通用、不审计、不守边界。**"本机信任 + 跨库 + 可审计 + 可不出网"的 AI 查询工作台是空位。**

## 2. 目标用户与洞察

### Persona 1 · 数据/后端开发者（第一优先级，基本盘）
- 行为：查多写少；库结构记不住；验证想法靠手写 SQL；关心"快"
- 我们的答案：一句话出结果、它记住你的库结构、安全兜底让你敢放手

### Persona 2 · 数据敏感团队里的非 SQL 专家（第二优先级，差异化放大器）
- 行为：向开发排队要数、怕碰生产库、不知道哪些数据能问
- 我们的答案：**只读连接赋予"敢问"的权限，AI 生成 + 黄卡确认 + 全程审计赋予"放心问"的安全**，自助查数不再依赖开发
- 为什么是放大器：DBeaver 只服务会写 SQL 的人；我们向下兼容开发者，向上打开"安全自助查数"的团队场景——这是对手给不了的增量

### 红利场景 · 团队/私有网关（形态演进）
同一个架构演进成团队网关：企业给整个数据团队一个可审计、可配置、数据不出内网的 AI 查数入口。**本地工具是信任验证场，网关是合规变现场**——先信得过，再发展开。

## 3. 差异化对照

| 维度 | DBeaver / Navicat | 云厂商 text-to-SQL | CLEARED |
|------|-------------------|--------------------|---------|
| 跨库 | ✅ 强 | ❌ 单云绑定 | ✅ 起步四种、可扩展 |
| 自然语言 → SQL | 弱（提示级） | ✅ | ✅ |
| 写保护闸门（本地、模型无关） | ❌ | 平台级权限 | ✅ 一个闸门管所有 |
| 审计可回溯（数字→SQL） | 弱 | 平台级 | ✅ 每个数字有出处 |
| 数据可不出内网 | ✅ | ❌ | ✅ 网关可配置 |

结论一句话：**拼"AI 多聪明"没有终局，拼"你敢不敢让它碰你的数据"才有护城河。**

## 4. 核心产品原则（五条，每一条都要能对着用户讲出口）

1. **信任优先**：一个闸门管 AI+手动；解析失败按写处理；写操作默认带预览、默认要确认（§7.10 最高信任档可在闸门范围内自动执行，物理安全网任何级别不可关）
2. **执行权默认在人，信任级别可调**：AI 是副驾——危险动作默认只给草稿+预览，方向盘默认在用户；用户可在会话级别选择更高信任档（见 §7.10）收窄确认，但物理安全网（闸门）任何级别不可关闭
3. **数字可回溯**：AI 给的每个数字都挂到一条被审计的 SQL——"报告里每句话都有出处"是企业审计的硬需求
4. **隐私边界由用户画**：默认只发结构不发行数据；敏感表可画红线屏蔽；数据流向（网关/本地/给谁）用户说了算
5. **机制 vs 内容分离（AI 哲学地基）**：系统层（代码 / 固化系统提示词）只做**通用机制**——结构化输出的框架、交互骨架（如点选 UI）、安全接通（闸门/审计/result_id）、聚合口径；**一切具体内容（澄清问题、候选选项、章节规划、叙述、口径）由模型基于当前库真实 schema + 数据动态生成**。代码与固化提示词中**零定制内容**——不出现针对具体库/场景的预设文案或逻辑（如"追问Q3是几月"）。**mock 演示兜底除外**（仅无 key 时承载演示；配置真实模型后全路径动态）。

## 5. 产品形态与交付

### 形态：本地 AI 优先查询工具（self-hosting Web），并把话说明白
- 产品是"浏览器工作台 + 本机 sidecar"，不是 Electron 桌面壳。
- **Why**：打包成本低、跨平台负担小、与"演进成团队网关"的浏览器形态天然兼容；桌面双端壳是纯成本、无差分价值。
- **对外口径修正**：全仓从"桌面数据库客户端"正名为**"本地 AI 优先的数据库查询工具"**——同类心智是 JupyterLab / Docker Desktop Web，诚实且不锁死。

### 交付：一条命令上手，首启即带信任叙事
1. `cleared` 一条命令：自动选端口、起 sidecar、开浏览器
2. 首启零成本：演示库 + mock 模型开箱即跑，无需任何 Key
3. 首启引导即产品叙事：连接 →「使用演示库」→ 第一轮对话讲清楚"AI 会写、但不危险"

## 6. 能力台阶（价值跃迁，不是功能清单）

每个台阶 = 用户能感知的能力跃迁 + 一个"激活时刻"。

| 台阶 | 能力 | 激活时刻 |
|------|------|---------|
| 1 信任底座 | 连得对（多源）、查得顺（编辑器/结果/审计）、玩得起（演示库+安全三色） | 提交带 WHERE 的 DELETE 被黄卡拦下、显示将影响 3 行——"它真的会挡" |
| 2 问得懂 | AI 副驾一句话出 SQL+结果+解读；还能**安全地改**（风险评估+人工确认） | "最近30天退货率最高的10个产品" → 绿卡自动执行 → 表格+解读——"它认得我的库" |
| 3 看得深 | 报告模式：澄清口径→章节分析→图表→数字可回溯 | 报告里"¥1.2M"点下去跳到生成它那条被审计的 SQL——"每个数字都有出处" |
| 4 记得住 | 知识库：领域标签、表语义、图谱检索 | 第二次问同主题，它直接说出上次建好的标签——"它记得我的业务" |
| 5 用得上 | 打包引导、敏感屏蔽、团队就绪 | 把 `payroll_*` 打上红线，AI 从此看不见——"数据边界由我画" |

## 7. 功能需求（按用户感知的模块组织）

### 7.1 连接中心
- 多数据源：SQLite / PostgreSQL / MySQL / KingbaseES 金仓起步（一期 4 个，见下），方言注册表可扩展
- **协议兼容优先的分层方言策略**（不按名气排序、按接入成本；覆盖企业/信创市场）：
  - 已支持：SQLite + PostgreSQL + MySQL（适配器 + 集成测试）
  - **Tier 1（协议兼容、近零成本）**：MySQL 兼容家族（OceanBase / TiDB / PolarDB）+ PG 协议家族（openGauss / KingbaseES）——现有 psycopg/aiomysql 即可连、sqlglot 方言基本覆盖，**验证后即可标注支持**，一掌覆盖国产化替代主流场景
  - **Tier 2（专有协议、中成本）**：达梦 DM（Oracle 风方言 + 专有驱动）——信创核心但需专门适配，视明确客户排期
  - **Tier 3（存量深、成本高）**：Oracle / SQL Server——大企业存量，驱动/方言/调优成本高，视明确需求排期
  - **产品边界 = SQL 协议**（比"关系型"标签更准）：NL→SQL 范式适配面即 SQL 协议——关系型 + 走 SQL 的 OLAP（Doris / StarRocks / ClickHouse 等，多兼容 MySQL/PG 协议，被 Tier 1 自然覆盖）；**非 SQL 协议（MongoDB / Redis / DynamoDB / ES 原生 DSL）查询模型不同，明确不进**（§10）
- **一期交付范围 + 新增成本（估）**：
  - **一期正式交付（已定 2026-08-18）：SQLite + PostgreSQL + MySQL + KingbaseES 金仓（PG 协议、近零成本）= 4 个**；**达梦视镜像/环境就绪**（就绪则加为第 5 个，否则延后）；**Oracle 延后到 V1.5 或按明确客户排**（成本最高 + 环境最难 + 一期 persona 使用率低——企业 Oracle 用户已有专属工具，替换门槛高）；Tier 1 兼容家族（OceanBase / TiDB / PolarDB / openGauss 等）V1 期间顺带点亮（验证即支持，不作正式验收项）
  - **新增一库的成本不在"SQL 执行"（通用）而在"元数据发现 + 驱动 + 集成测试环境"**：
    - 协议兼容（Tier 1）：~0.5–2 天/库（多为配置 profile + 起 docker 验证，元数据查询沿用母协议）
    - 专有协议（达梦）：~3–5 天 + 环境（专有驱动、元数据发现改写为 Oracle 风、难找可用镜像）
    - 存量协议（Oracle / SQL Server）：~5–10 天/库（驱动 + 方言差异多：分页/类型/系统表查询）
  - **判断**：Tier 1 几乎免费，是隐藏卖点——国产库 + 国产 OLAP 大多落在 Tier 1，恰好是"中国企业中 AI 查数最可能被用上的那一批"
- **真实环境验收（发布硬门槛）**：V1 发布前必在真实 PG 与 MySQL 业务库各完成一次全链路验收——连接测试、schema 发现、AI 查数、写操作（风险评估+确认）、报告模式、标签路由、敏感屏蔽、审计；**只在 demo 库 + mock 上验证不构成"能连真实库"的交付**
- **只读连接**：授予"敢问"而"写不了"的权限；敏感表/列可一键屏蔽（见 §7.6）
- 连接测试、凭据可选本地加密（二期）

### 7.2 查询工作台
- SQL 编辑器：格式化、选中片段问 AI、快捷键
- 结果表格：分页/排序/列过滤、大整数不丢精度、行数上限保护
- 查询历史与审计页：运行过的每一条都找得回

### 7.3 AI 副驾（主场景：答得准 · 答得漂亮 · 答不对会回头）
- 自然语言 → SQL → 安全三色卡片 → 一句人话解读
- **答得准（上下文策略）**：
  - 上下文 = schema 摘要（只结构、永不明细）+ 会话历史 + 知识库轻量记忆（§7.5）
  - **长会话窗口管理（V1）**：超窗按"优先级 + 时间"截断（留最近 N 轮 + 关键字段：连接/当前表/最近约束）；**不做 LLM 摘要压缩**（二期考虑——摘要会失真且费时）
- **答得漂亮（结果呈现）**：
  - 绿卡只读自动执行（默认档）→ 结果进工作区表格 + 一句人话解读
  - **人话解读（已定：聚合为主、明细需授权；V1 粒度）**：默认基于列名 + 行数 + 聚合统计生成，不引用具体行值；允许解读聚合统计本身（趋势判断基于已统计维度）但**禁止编造未统计过的结论**（诚实边界）；用户对某次结果显式"要求解释"才临时授权该结果集（授权限当次、不进会话历史常驻）
  - 卡片 = SQL 双层编辑器，可改、可重跑、可"解释/优化"（选中问 AI）
  - **就当前结果继续追问（V1）**：支持"看到退货率 12% 后追问：哪个品类最高"——上下文带上前一条 SQL 形成追问链；不做网格级复杂钻取
- **答不对会回头（多轮，V1 分级应对）**：
  - 结构可判定的错误（表/列不存在、语法错误）→ AI 必须立即明确告知，**不硬编卡片**（避免幻觉）
  - 语义不确定（指标口径歧义，如"客单价 vs ARPU"）→ 才向用户澄清 / 追问
  - query 模式不做"每问必澄清"；报告模式的澄清机制（§7.4）自成一套
- **分步输出（阶段化 · 真实阶段产物，用户认可 2026-08-18）**：
  - 问题提交后四阶段逐步输出：**意图 → 检索定位 → SQL 生成 → 安全评估**，每步可展开看**真实执行产物**（意图→真实分类结果；检索→真实标签路由候选表清单；SQL→真实生成 SQL；评估→真实闸门三色 verdict），与"数字可回溯"一致
  - **摘除 mock 播放器**：现有 `THINK_LINES` 按关键词硬编码的思考文案 + 固定延时逐行播放属于定制化内容，**摘除**——四步机制保留、内容来源换成真实产物（§4 原则 5 机制 vs 内容分离）；配真实模型后全动态
  - **不展示模型思考正文**（reasoning 原文）：思考链不可控、会暴露试错/犹豫，对信任产品是负资产；只展示可追溯的真实阶段产物
- **写操作（§7.9 / §7.10）**：增删改全支持，风险评估面板（影响范围/行数/等级）+ **默认人工确认**（信任级别可调，见 §7.10）
- **DDL**：红卡草稿发编辑器，AI 没有执行权（物理不存在）
- 思考强度四态（关/低/中/高），按模型能力显隐；"模型可见了什么"界面常驻

### 7.4 分析报告
- **定位**："看得深"台阶的载体——从"查一个数"到"分析一段话"，面向个人深度分析 + 团队汇报
- **天然只读，与信任级别正交**：报告工具集不含任何写工具（物理写不了），会话信任级别（§7.10）对报告无影响——最大信任档也不会让报告写库
- **数据口径 = 聚合为主（与 §7.3 一致）**：喂模型的是 GROUP BY 聚合统计，明细行永不回传；"模型可见：N 个聚合结果集"常驻标注
- 报告模式：澄清口径 → 规划章节 → 逐章执行 → 汇总成文；每章 = 查询（过闸门+审计）+ 图表 + 叙述，**叙述数字挂 result_id 可点回来源**；报告为快照（生成时刻固化）
- **失败处理（V1 · 单章降级）**：某章取数失败只降级该章（标"取数失败 + 原因"），其余章节照常成文、报告整体仍交付并注明缺章——一章坏不拖垮整份
- **澄清交互（V1 · 选项化 + 机制生成）**：澄清以可点选候选呈现（时间/维度），**候选由模型基于当前 schema 动态生成、代码零预置**；不答 / 超轮数 → 按默认口径生成并在报告标注"按默认口径"
- **生成体验（V1 · 渐进 + 可离开）**：每章完成即推一张卡，可中途离开，快照机制保证重开即看生成时的结果
- **模板复用（不做）**：V1 不提供报告模板 / 一键套用（涉及时间/口径变量替换），留 V2
- 完整设计见 `docs/superpowers/specs/2026-08-16-report-mode-design.md`（澄清/计划/章节/数字回溯/快照/只读工具集），本 PRD 只定其产品定位、交互取舍与「机制 vs 内容」红线（§4 原则 5）
- 报告导出/分享（HTML/PDF）为 V2.0

### 7.5 知识库（用户已定：完整版作 V1 亮点 · "记得住"）
- **定位**：完整版作 V1 亮点叙事——领域标签 / 知识图谱 / 标签路由是"记得住"台阶的主角，不只是辅助功能。
- 领域标签体系：AI 从真实结构"长"出来、人工确认后生效、每库一套；标签确认 / 图谱可视化的交互打磨（北欧视觉）
- **标签确认体验（V1，避免打扰）**：默认"整库一键确认 + 单个驳回"，不逐条点确认；未确认标签可进入路由，但 AI 回答标"未确认标签"，确认后转正——有获得感又不阻塞
- **图谱即入口（V1，不是陈列柜）**：图谱节点可点击 → 触发该表的预览 / AI 问答 / 数据，让"看得深"与"记得住"串起来
- **结构变更提醒（V1）**：定时轮询表结构（默认每小时、间隔可配如 10 分钟），检测变化即提示"知识库可能过时，重建？"——只提醒不自动重建（避免打断）
- 表/字段语义注释；标签驱动路由：意图 → 标签 → 相关表 → 只喂相关结构（复杂多表库上回答质量的杠杆）
- **两段式定位（大库场景的答案，用户确认 2026-08-18）**：意图 → **① 标签定位范围**（图库+FK 邻近扩展收敛，不把 1000 表塞进上下文）→ **② 注释理解语义**（候选范围内用字段注释翻译列含义 → 写准 SQL）。标签管范围、图谱管导航、注释管语义，三者各司其职
- **路由邻近兜底**：候选子图按 FK 做上/下游扩展（step 扩展），防止问题跨标签域时漏表
- **范围可见可纠正**：AI 呈现"已锁定的候选表"清单，用户可纠正——大库下漏表能被指出，不做黑盒定位
- **标签粒度**：以"业务域"为粒度收敛（订单域/客户域），不碎成单表级
- **"记得住"证据可见（亮点不虚的前提）**：AI 回答 / 报告引用知识库来源（"来自标签「订单域」+ 表 orders·order_items"），让用户能感知知识库在工作
- **效果指标（预留，V1 先不定）**：预留"标签路由命中率 / 多表问题答准率"等指标位，V1 不立量化指标（口径未定，避免口号化）
- **验收门槛**：V1 发布前完成"多表复杂库上标签路由质量验收"，把"第二次问答命中上次建好的标签"做成可复现的演示场景
- 存储可插拔（内存模拟 / 本地语义嵌入可选），单机默认哈希向量；构建懒加载一次、重启从 `knowledge-{conn_id}.json` 恢复
- **存储决策（已定 2026-08-18）**：**本地单机自研轻量存储**，不引入 qdrant / neo4j 作为运行时依赖——部署负担致命（本地工具不能让用户先装两个服务）、规模不匹配（单机几千表/几万边/几千向量 dict 遍历 + 暴力 kNN 毫秒级）、所需图/向量能力浅（FK+值重叠+标签分组、不用图算法）。**安全阀**：存储层抽象为 `VectorIndex` / `GraphStore` 接口 + 契约测试钉死，切换第三方始终可选；**企业版 / 团队网关（V1.5+）按规模评估引入 qdrant / neo4j**
- **自研原语范围（明确支持 / 不支持）**：支持 = 邻接表图遍历（BFS/DFS、连通分组、2 步扩展）+ **暴力 kNN 余弦相似度（原生支持，毫秒级）**；不支持 = Cypher 查询语言、ANN 索引（HNSW/IVF）、图算法（社群/中心性/模式匹配）。**Cypher 是明确 non-goal**——图当"遍历结构"走接口方法而非查询语言；**需要 Cypher / ANN 的时刻 = 切换 neo4j / qdrant 的触发信号本身**。复杂度评估：两原语均为数据结构入门级，非高级工程；实施期先做这两个原语的契约测试小原型验证（消除"走不通"焦虑）
- **自研的质量底线（回应"有没有实力 / 能不能用起来"）**：检索质量由**嵌入**决定、不由引擎决定——自研只做"FK 邻接 BFS 遍历 + 暴力 kNN"，不追求算法先进；**真正决定"用起来"的是嵌入质量（本地 bge-m3）+ 注释/标签内容 + onboarding 引导，不是引擎**——投入优先放在接对嵌入与产品导流，而非自研 ANN / 图算法。质量底线 = 结果正确（契约测试钉死）+ 响应毫秒级 + 接口稳定。
- **切换触发信号（写死）**：单连接上万表 / 向量超 ~5 万需真 ANN / 要全文语义检索大文档时，才评估切 qdrant / neo4j——**由规模触发，不由"自研不顺"触发**
- **知识库可扩展内容（用户确认，后续补充）**：不止定位/语义/记忆——还可能有历史问题沉淀模板、SQL 参数映射语义等；均为内容层（追加+检索），不改变上述存储决策

### 7.6 隐私与数据边界
- **敏感名单（R1）**：连接级表/列 glob（`payroll_*`），屏蔽项不进发模型的上下文、不入知识库；不影响用户直接执行
- **明细授权（R1，配合 §7.3 解读）**：AI 读取明细行（含聚合统计）一律经显式授权，授权限单次、结果集不进会话历史常驻；"模型可见了什么"清单如实反映每次授权
- **对话历史脱敏（R2 预留）**：发送前对高熵字面量（邮箱/号/卡）打码；自动检测误伤高，二期再做
- 数据流向可配置：云端 / 本地 / 私有网关，用户决定数据去哪

### 7.7 审计与合规
- **所有真实执行都入审计**：手动、AI 卡片、AI 对话内部探测、报告子查询——统一记录、可区分来源
- 审计页按连接/时间/来源过滤；报告子查询挂同一报告 ID，一份报告的完整查询链一眼可见

### 7.8 设置与部署
- 模型管理：多模型、按对话切换、能力探测徽标（连通/函数调用/流式/推理/推理深度/上下文）
- **激活门槛（用户补充 2026-08-18）**：配置大模型后**必须测试通过才激活**——测试失败 / 未测试标"未激活"，对话框模型选择器只列已激活模型（未激活仅设置页可见），默认模型必须是已激活；激活 = 测试通过（连通 + 能力探测）
- **推理深度（用户补充）**：能力徽标含"推理深度 / 支持档位"；探测为 best-effort（模型名推断 + 实测），**可手动覆盖、诚实标注不可靠**——档位适配尽力而为，不做假精确（对应 §7.3 思考强度按能力显隐）
- **对话框模型选择器 = 能力驱动**：切换模型时按该模型能力展示可用选项（是否推理 → 思考强度控件显隐；支持档位 → 可选力度）
- 运行参数：行数上限、连接池大小、数据目录/端口/鉴权只读展示

### 7.9 AI 写操作与风险评估（用户最大调整）

**目标**：AI 交互区从"只能查"进阶为"能安全地改"——完整支撑 INSERT / UPDATE / DELETE，让"让 AI 帮你改数据"成为可信体验。核心杠杆不是放权，而是**把风险评估做成可感知的产品界面**（已与负责人确认：默认人工确认 + 风险评估证据化；会话信任级别最高档可在闸门范围内自动执行，见 §7.10）。

**需求**：
- **Req 5.1 增删改全支持**：AI 可生成 INSERT（单/多行）、UPDATE、DELETE（含批量语义），并给出对应的写操作卡片。
- **Req 5.2 风险评估证据化（核心差异）**：每次写操作 AI 产出结构化评估面板，不止"影响 N 行需确认"：
  - 影响对象：目标表 + 条件覆盖（有无 WHERE / 命中哪些列 / 是否走索引）
  - 预估影响行数：COUNT 实测（沿用闸门 preview），来源可见
  - 风险等级：低 / 中 / 高，附**判定依据**（为什么是这一级）
  - 可回滚性标注：一期如实标注"不可回滚，请谨慎确认"（回滚整体暂缓与「验证后提交」设计见下一条）
- **Req 5.3 执行权默认在人**：写操作默认黄卡确认；确认时后端**重新评估**（防 TOCTOU，保留既有不变式）；仅在 §7.10 最高信任档下，闸门放行范围内的写操作可免确认自动执行。
- **Req 5.4 强审计**：所有增删改查记录日志且可追溯，写操作必含影响行数与风险评估快照（等级 + 依据），事后可复现"当时为何放行"。
- **Req 5.5 交互形态**：写操作卡 = SQL 双层编辑器 + 可展开的风险评估面板 + 确认按钮；评估证据默认展开（不用点才看），强化"AI 会为自己写的每一句负责"的观感。
- **回滚：一期不做（暂缓）**：不提供提交后撤销（任何客户端的常态，如实标注"不可回滚"、靠审计留档兜底）；不做客户端快照回滚、不做 AI 生成反向 SQL、不做"可恢复性评估"模糊中间态。事务化「验证后提交」设计（DB 原生事务、确认点即提交/回滚、防孤儿事务超时）已定稿，留待后续迭代按需启用。

**边界（明确不做）**：
- AI 默认不自动执行写操作（人工确认）；§7.10 最高信任档可在闸门放行范围内自动执行，物理安全网不可关闭
- DDL 仍仅手动，AI 只有 draft_ddl（物理边界不动）
- 不做 AI 生成式回滚、不做"可恢复性评估"类模糊中间态、**不做客户端快照回滚**；回滚只认**数据库事务**（提交前可回滚，提交后不可撤销并如实标注），恢复走 ROLLBACK / 事务兜底
- 不自动包裹事务 / 不改闸门三档；恢复方式以"建议"形态给出，执行与否与执行方式由用户决定
- 高风险（无 WHERE / 影响过大）采用更强确认（红卡级文案 + 二次确认输入）

**为什么这是信任能力的升级**：原"写操作黄卡确认"是底线；本需求把同一底线升级为**"AI 评估给你看 + 人决定 + 全程可追溯"**的可交互信任界面——不会因为风险面板而拖慢常用操作，反而让"确认"变成有信心的一按，这正是"信得过"的具体形态。

### 7.10 会话信任级别（HITL 介入粒度的控制）

用户可在 AI 对话会话级选择信任级别，控制人工确认（HITL）介入的粒度：

| 级别 | 读（SELECT） | 写（INSERT/UPDATE/DELETE） | 适合 |
|------|-------------|------------------------------|------|
| 全部介入 | 人工确认 | 人工确认 | 首次使用 / 高价值库，最多把关 |
| **读自动 · 写确认（默认）** | 自动执行 | 人工确认 | 查多写少场景的日常档 |
| 读写自动 · 最大信任 | 自动执行 | 闸门范围内自动执行 | 唯一可让 AI 自动写数据的档，须显式开启 + 二次确认 |

**HITL 决策矩阵（三者共同决定）**：每个 SQL 执行前强制进入安全闸门（本地、模型无关、离线也拦），闸门先判定**脚本类型 + 兜底风险**（tier / verdict / 无 WHERE / 影响行数），再叠加**会话信任级别**决定最终确认粒度——**职责分离**：闸门管"险不险"，信任级别管"要不要人确认"，两层不互相覆盖。

| 脚本类型 \ 信任级别 | 全部介入 | 读自动·写确认（默认） | 读写自动·最大信任 |
|------|------|------|------|
| 读 SELECT | 需确认 | 自动执行 | 自动执行 |
| 写·低风险（有 WHERE 且影响 ≤N） | 黄卡确认 | 黄卡确认 | 自动执行 |
| 写·高危（无 WHERE / 影响过大 / 歧义） | 红卡确认 | 红卡确认 | **红卡确认（不豁免）** |
| DDL（AI） | 仅草稿不可执行 | 仅草稿不可执行 | **仅草稿不可执行（物理不变）** |

读法：**最高信任档只豁免"闸门判定为安全的低风险写"的人工确认；高危写与 DDL 永远回到人**——这就是"AI 能写，但永远写不危险"的执行路径。

**关键不变式（与闸门正交）**：
- 信任级别控制的是"是否要人工确认"，**不是"是否可用安全网"**。闸门（模型无关、本地规则、离线也拦）在任何级别都保持物理防线：无 WHERE 写、影响过大、DDL（AI 无执行工具）不会被任何级别"放行"。
- **默认 = 读自动 · 写确认**；最高信任档须显式开启 + 二次确认（"你要让 AI 直接改库，确认吗"）。
- **审计不分档，全档同权**：所有真实执行（含 AI 对话内部读）都记录——语句、判定、影响行数、耗时、来源；自动执行档责任更高，记录只多不少。
- 级别为会话级，切换即时生效；`read_only` 等连接内建约束不随级别变化。
- 回滚不随级别变化：一期均不提供提交后撤销（见 §7.9），如实标注"不可回滚"、靠审计兜底。

## 8. 关键体验设计（让信任可见、可交互，而不是口号）

- **安全三色是全局唯一彩色语言**：绿=读（直通）、黄=写（确认）、红=DDL（仅手动），任何卡片一眼读情绪
- **"执行权默认在人，信任级别可调"**：AI 给的永远是草稿+预览；绿卡只读可自动执行，黄卡默认等人按；会话信任级别（§7.10）是这套默认交互的可调旋钮
- **数字可追问**：任何一个数字 → 来源 SQL → 审计记录 → 原始表（一版先做点到审计的轻量回溯）
- **首启即验证信任**：第一轮对话就让你看到"AI 会写、但不危险"，把产品哲学做成上手体验本身

## 9. 现状锚点（发布前必须收口的信任承诺）

以下为当前实现与 §4 原则的差距，**制度性地在 V0.5 收口**——它们是"原理说了、路径没做全"的承诺缺口，不是偶发 bug：

| 承诺 | 当前状况 | 收口方式 |
|------|---------|---------|
| "每条真实执行都入审计" | AI 对话内部为取行数而真实读库的查询**不入审计** | 补入审计并标记来源；同一条 SQL 不"内部读一遍+卡片再跑一遍"（消除双执行） |
| "按对话切模型 + 思考强度"在所有模式生效 | 报告模式**忽略** `model_id` 与 `reasoning`（静默用默认模型不思考） | 抽取共享解析，报告与查询行为一致 |
| "敏感数据边界由用户画" | 尚无敏感表/列屏蔽能力 | 连接级 glob 名单 + 上下文/知识库剔除 |

## 10. 非目标与边界

- 不做跨库联邦 JOIN（ETL 工具的地盘）
- 不做自动 PII 检测一期（误伤高）；只做敏感 schema 屏蔽 + 预留脱敏接口
- 不做团队网关多用户一期（先本地工具验证信任，再演进形态）
- 不改变"DDL 永不进 AI"的物理边界（这是防风险的最后底线）
- 一期不提供提交后回滚（任何客户端常态）；回滚按「验证后提交」事务化设计暂缓，见 §7.9
- 不做非 SQL 协议数据库（文档 / 键值 / 图 / 检索原生 DSL，如 MongoDB / Redis / DynamoDB / Elasticsearch）——产品边界是 SQL 协议，NL→SQL 范式才成立；走 SQL 的 OLAP（Doris / StarRocks / ClickHouse）由协议兼容自然覆盖
