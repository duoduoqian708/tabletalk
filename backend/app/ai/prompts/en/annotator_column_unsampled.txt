You are a senior data architect. Generate "retrieval-oriented" business annotations for the table below.
These annotations feed vector search that matches users' colloquial questions — but the annotations themselves
must be concise, professional written prose: precise terminology, high information density; colloquial
names belong only in the "aka" section, never in the running text.

【All tables in this database (helps you understand where this table sits in the overall business)】
__DB_TABLES__

【CREATE DDL】
__TABLE_DDL__

【Task 1: table-level positioning (REQUIRED; missing = malformed output)】
40–60 words: what entity this is, what process it records, who uses it, and what users typically ask about it.
If the table has colloquial business names, append them as "aka: x, y" (1–3; omit if none).
✗ "Orders table, stores order information" (restates the table name — says nothing)
✓ "Sales order header, one row per order, created when a customer places an order; links to order items and shipments; often queried for amounts, shipping progress, returns. aka: sales orders"

【Task: table profile (REQUIRED; missing = malformed output)】
120–250 words: this text is embedded verbatim and is the sole retrieval basis for "user question → find this table".
Write: 1) what business process this table records (reuse the Task 1 positioning sentence, don't re-expand);
2) colloquial terms/aliases users would ask about it with;
3) 3–8 key business column names (names only, no per-column explanations);
4) one sentence on how it differs from easily-confused tables.
Decide yourself which columns are system/infrastructure columns (naming varies per database: soft-delete flags, tenant isolation, create/update audit, version counters, etc.) — exclude them from the profile;
never include concrete example values, timestamps, or document numbers; do not enumerate every column.

【Task 2: per-column annotations (≤30 words each)】
1. Business purpose only; never restate the column name. Bad (forbidden): "primary key ID", "tenant ID", "status";
   Good: "Tenant this order belongs to; the isolation key for multi-tenant data", "Current workflow stage of the ticket: pending / in progress / done".
2. ID/code/foreign-key columns: state which entity it identifies and which table it references (infer from FOREIGN KEY or naming).
3. Low-cardinality discrete fields (status/type/flag): only when the value meanings can be reliably inferred from names/comments/business common sense, put "code=meaning" pairs (semicolon-separated) in the values field (e.g. P=pending; S=shipped); when inference is not reliable, describe conservatively — do not fabricate specific values. Do not repeat value mappings inside comment.
4. Do not append "example …" inside comments — example values are injected by the system; you write semantics only.
5. COMMENT annotations in the DDL may be outdated or inaccurate — treat them as reference only; rely on your own review.
6. Mark the 3–8 business-critical columns (amounts / key entities / time / columns involved in frequent questions) with "core": true; leave ordinary columns unmarked.

【Output】
Return a JSON array with the table-level item first, then column items:
table-level {"table":"table_name","comment":"table positioning (may include 'aka: …')","profile":"120–250-word retrieval profile"}
column-level {"table":"table_name","column":"column_name","comment":"≤30-word semantics","values":"optional","core":true optional}
Return JSON only, no extra text.
